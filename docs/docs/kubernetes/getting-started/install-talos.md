# Install Talos

This page covers going from VMs in maintenance mode (created by [Terraform](/kubernetes/getting-started/deploying-the-infrastructure)) to a bootstrapped Talos cluster with a `talosconfig` and `kubeconfig`. At the end, the nodes are `NotReady` because there is no CNI yet. [Bootstrap the cluster](/kubernetes/getting-started/bootstrap) installs Cilium and Flux.

## topf

[topf](https://postfinance.github.io/topf/main/) (PostFinance) is "a single binary that handles the full lifecycle of a Talos cluster": it generates and stores the secrets bundle, assembles machine configs from layered patches, applies them with diffs and confirmation, bootstraps etcd, upgrades Talos, and issues `talosconfig`/`kubeconfig` ([topf docs](https://github.com/postfinance/topf/blob/main/docs/index.md)). It does not manage Kubernetes upgrades; use `talosctl upgrade-k8s` for those ([Kubernetes upgrade](https://github.com/postfinance/topf/blob/main/docs/kubernetes-upgrade.md)). onedr0p/cluster-template [replaced talhelper with topf](https://github.com/onedr0p/cluster-template/pull/2293) in July 2026, and talhelper itself is [archived](https://github.com/budimanjojo/talhelper/releases/tag/v3.1.17).

Current release: **v0.6.2** ([releases](https://github.com/postfinance/topf/releases)). topf isn't in nixpkgs, so `devenv.nix` installs the pinned release binary (see [Local tools](/kubernetes/getting-started/deploying-the-infrastructure#local-tools)). `devenv shell` also provides `talosctl`, `kubectl` and `yq`, and sets `TALOSCONFIG` and `KUBECONFIG` to the files `just talos::create` writes.

:::note Versions

topf v0.6.2 reports `topf version 0.6.2 (Talos v1.14.4)`: it is built against the Talos 1.14 machinery. The cluster runs **Talos 1.14.5**, the version the VMs booted and the `talosctl` in devenv. `talos_version` in `infrastructure/variables.auto.tfvars` matched `talosVersion` in `talos/topf.yaml` when the VMs were created, but it is only the boot image for new VMs. Upgrades bump `topf.yaml` alone: changing the tfvars recreates every VM ([Upgrades](/kubernetes/upgrades)). **Kubernetes 1.37.2**: `talosctl` 1.14.5 defaults to 1.37.1, and the `ghcr.io/siderolabs/kubelet:v1.37.2` image exists. A rendered config with 1.37.2 passes `talosctl validate --mode metal --strict`. Check topf's release notes before moving to a new Talos minor version.

:::

topf reads SOPS-encrypted files by **running the `sops` binary** (`sops filestatus` / `sops decrypt`) ([source](https://github.com/postfinance/topf/blob/main/internal/sops/sops.go)). So decryption goes through `gpg` and the YubiKey like any other `sops` call ([SOPS](/kubernetes/sops)).

## The `talos/` directory

```
talos/
├─ topf.yaml               # cluster + nodes
├─ schematic.yaml          # Image Factory extensions (see "Deploying the infrastructure")
├─ secrets.sops.yaml       # Talos secrets bundle, generated by topf, SOPS-encrypted
├─ mod.just                # just talos::* recipes
├─ all/                    # patches for every node
│  ├─ 00-install.yaml
│  ├─ 01-hostname.yaml.tpl
│  ├─ 10-network.yaml
│  └─ 20-longhorn.yaml
└─ control-plane/
   └─ 00-cluster.yaml
```

Patches merge in the order `all/` → `<role>/` (`control-plane/` or `worker/`) → `node/<host>/`, lexicographically within each folder, with later patches winning. Files ending in `.yaml.tpl` are Go templates with access to `.Node.Host`, `.Node.IP`, `.Node.Data.*` and more. JSON6902 patches are **not supported** ([configuration model](https://github.com/postfinance/topf/blob/main/docs/configuration-model.md)). This is the same layout cluster-template uses ([`talos/README`](https://github.com/onedr0p/cluster-template/blob/main/template/config/talos/README.md.j2)).

Rendered machine configs contain the cluster CA keys in plain text. `.gitignore` excludes `talos/rendered/` and `talos/output/` (where `topf render` writes), as cluster-template does ([PR #2293](https://github.com/onedr0p/cluster-template/pull/2293)), plus `talosconfig` and `kubeconfig`.

### `topf.yaml`

```yaml
---
clusterName: homelab
clusterEndpoint: https://10.0.11.10:6443   # the API VIP
kubernetesVersion: 1.37.2
talosVersion: 1.14.5                       # bump + `just talos::upgrade`; NOT talos_version in the tfvars (docs: Upgrades)
schematicId: "@schematic.yaml"
platform: nocloud                          # matches the nocloud image Terraform boots
secretsPath: secrets.sops.yaml

nodes:
  - host: talos-1
    ip: 10.0.11.1
    role: control-plane
  - host: talos-2
    ip: 10.0.11.2
    role: control-plane
  - host: talos-3
    ip: 10.0.11.3
    role: control-plane
```

The fields are from the [topf configuration reference](https://github.com/postfinance/topf/blob/main/docs/configuration.md):

- **`clusterName`, `clusterEndpoint`, `kubernetesVersion` and `nodes`** are required.
- **`talosVersion` + `schematicId` + `platform`** make topf inject the installer image `factory.talos.dev/<platform>-installer/<schematicId>:v<talosVersion>`. On Talos ≥ 1.14 this goes into an `UnattendedInstallConfig` document ([upgrade: installer image](https://github.com/postfinance/topf/blob/main/docs/commands/upgrade.md#installer-image)).
- **`schematicId: "@schematic.yaml"`** computes the ID locally from the file.
- **`secretsPath`** overrides the default `secrets.yaml`.

The endpoint is the API VIP from the [network map](/kubernetes/intro#network-map). That's fine for Kubernetes clients, but the Talos API must not go through the VIP ([VIP docs](https://docs.siderolabs.com/talos/v1.14/networking/advanced/vip.md)). `topf talosconfig` already sets the control-plane node IPs as endpoints ([talosconfig](https://github.com/postfinance/topf/blob/main/docs/commands/talosconfig.md)).

## Patches

### `all/00-install.yaml`

```yaml
apiVersion: v1alpha1
kind: UnattendedInstallConfig
provisioning:
  diskSelector:
    match: disk.dev_path == "/dev/sda"
```

`talosctl get disks --insecure` shows the same layout on all three VMs: `sda` (54 GB, the `scsi0` system disk), `sdb` (215 GB, the `scsi1` Longhorn disk) and `sr0` (4.2 MB, read-only, `cdrom: true`: the cloud-init drive). This is the topf getting-started patch for Talos ≥ 1.14 ([getting started](https://github.com/postfinance/topf/blob/main/docs/getting-started.md)), adapted from `/dev/vda` to the SCSI disk Terraform creates. The installer **image** isn't set here because topf injects it from `topf.yaml`. Fields per the [UnattendedInstallConfig reference](https://docs.siderolabs.com/talos/v1.14/reference/configuration/runtime/unattendedinstallconfig.md). `UnattendedInstallConfig` and the deprecated `.machine.install` are mutually exclusive.

### `all/01-hostname.yaml.tpl`

```yaml
apiVersion: v1alpha1
kind: HostnameConfig
auto: "off"
hostname: {{ .Node.Host }}
```

topf's `host` is **not** applied as the Talos hostname by default. This template is the documented fix ([getting started](https://github.com/postfinance/topf/blob/main/docs/getting-started.md)).

### `all/10-network.yaml`

```yaml
apiVersion: v1alpha1
kind: KubeNetworkConfig
podSubnets: ["10.244.0.0/16"]
serviceSubnets: ["10.96.0.0/12"]
---
apiVersion: v1alpha1
kind: ResolverConfig
nameservers:
  - address: 10.0.1.30   # LAN DNS server (see the network map); no public fallback
```

- **`KubeNetworkConfig`**: the cluster-internal CIDRs from the [network map](/kubernetes/intro#network-map), written out explicitly ([KubeNetworkConfig reference](https://docs.siderolabs.com/talos/v1.14/reference/configuration/kubernetes/kubenetworkconfig.md)). Patches *replace* these lists rather than appending to them ([patching](https://docs.siderolabs.com/talos/v1.14/configure-your-talos-cluster/system-configuration/patching.md)).
- **`ResolverConfig`**: same shape as [cluster-template's](https://github.com/onedr0p/cluster-template/blob/main/template/config/talos/all/21-network.yaml.j2). The only nameserver is the LAN DNS server `10.0.1.30`, so every lookup, including local-only names, gets the same answer. Jonas adds `1.1.1.1` as a fallback after his router ([post 2](https://jonashietala.se/blog/2026/05/22/talos_linux_on_proxmox_with_terraform)); I don't. `10.0.1.30` runs outside the cluster, so the nodes don't need the cluster up to resolve names. The trade-off: if `10.0.1.30` is down, the nodes can't resolve anything, including image registries.

Node addresses aren't in any patch. They come from the Proxmox cloud-init data that Terraform sets (`10.0.11.x/16`, gateway `10.0.0.1`), which the `nocloud` platform reads, as in Jonas's setup ([post 2](https://jonashietala.se/blog/2026/05/22/talos_linux_on_proxmox_with_terraform), [nocloud docs](https://docs.siderolabs.com/talos/v1.14/platform-specific-installations/cloud-platforms/nocloud.md)).

### `all/20-longhorn.yaml`

The Longhorn data disk as a Talos user volume. The details and sources are on [Storage: Longhorn](/kubernetes/storage-longhorn#talos-machine-config).

### Control-plane patches

`control-plane/00-cluster.yaml`:

```yaml
# Cilium replaces Flannel and kube-proxy
apiVersion: v1alpha1
kind: KubeFlannelCNIConfig
$patch: delete
---
apiVersion: v1alpha1
kind: KubeProxyConfig
enabled: false
---
# All nodes are control planes and run workloads
apiVersion: v1alpha1
kind: KubeNodeConfig
taints:
  node-role.kubernetes.io/control-plane:
    $patch: delete
---
# Kubernetes API VIP (see the network map)
apiVersion: v1alpha1
kind: Layer2VIPConfig
name: 10.0.11.10
link: eth0
```

Each document and where it comes from:

- **`KubeFlannelCNIConfig` / `KubeProxyConfig`**: the Talos 1.14 patch from the [Talos Cilium guide](https://docs.siderolabs.com/kubernetes-guides/cni/deploying-cilium.md). Jonas's 1.12-era `cluster.network.cni.name: none` and `cluster.proxy.disabled` fields are deprecated in 1.14 ([What's new](https://docs.siderolabs.com/talos/v1.14/getting-started/what's-new-in-talos.md)).
- **Taint removal**: copied from [cluster-template's control-plane patch](https://github.com/onedr0p/cluster-template/blob/main/template/config/talos/control-plane/00-cluster.yaml.j2), which topf renders and CI validates with `talosctl validate`.
- **`Layer2VIPConfig`**: from the [VIP docs](https://docs.siderolabs.com/talos/v1.14/networking/advanced/vip.md). It is for control-plane nodes only, needs etcd up (so it appears after bootstrap), and the nodes must share an L2 segment, which the flat `/16` provides. Jonas's Proxmox VMs used `eth0` ([post 2](https://jonashietala.se/blog/2026/05/22/talos_linux_on_proxmox_with_terraform)). Here too: `talosctl get links --insecure` shows `eth0` as the only link that is up on all three VMs.

**CoreDNS** stays Talos-managed: it's deployed unless `KubeCoreDNSConfig` disables it. cluster-template disables it and installs the chart instead.

**Pod Security** stays at the Talos default. Talos applies the `baseline` profile to all namespaces except `kube-system` ([Longhorn Talos page](https://longhorn.io/docs/latest/advanced-resources/os-distro-specific/talos-linux-support/)), so namespaces that need privileged pods, such as `longhorn-system`, get an `enforce: privileged` label. cluster-template deletes the PodSecurity admission config instead.

## Create the cluster

Inside `devenv shell`, with the YubiKey plugged in:

```bash
just talos::create
kubectl get nodes        # three control-plane nodes, NotReady until Cilium is installed
```

`talos/mod.just` (`just talos::create`) runs these steps from `talos/`:

```bash
# 1. Secrets bundle: generated once, written SOPS-encrypted; abort unless sops says it's encrypted
topf secrets --confirm=false > /dev/null
sops filestatus secrets.sops.yaml          # {"encrypted":true}

# 2. Show the diff, ask, apply to the maintenance-mode nodes, bootstrap etcd
topf apply --auto-bootstrap

# 3. Client configs (gitignored); just talos::configs re-runs only this step
topf talosconfig > talosconfig
topf kubeconfig --validity 8760h > ../kubeconfig
```

- **`topf secrets`** generates the bundle if none exists. It is "SOPS-encrypted on write if a corresponding SOPS config is found" ([secrets](https://github.com/postfinance/topf/blob/main/docs/commands/secrets.md)). Run from `talos/`, topf finds the repo-root [`.sops.yaml`](/kubernetes/sops#sopsyaml), and its `talos/` rule encrypts the whole file to the YubiKey PGP key and the age key. I checked this with a throwaway bundle. Generating only encrypts, so it needs the public keys but not the YubiKey. Every later read decrypts, so it does need the YubiKey. topf prompts before generating unless you pass `--confirm=false`. The bundle goes to stdout (redacted by default, `--redact`), so the output is discarded.
- **`topf apply`** runs pre-flight checks, shows a diff and asks for confirmation. The recipe doesn't pass `--confirm=false`, so you always see the diff first. On fresh maintenance-mode nodes it skips post-apply checks. `--auto-bootstrap` calls the etcd bootstrap API on the first control-plane node, retrying for up to 10 minutes ([apply](https://github.com/postfinance/topf/blob/main/docs/commands/apply.md)).
- **`topf talosconfig` / `topf kubeconfig`** both print to stdout. The recipe writes them through a temp file with `umask 077`. `topf kubeconfig` issues a `system:masters` cert that is valid for 12h by default. cluster-template passes `--validity 8760h` to get a long-lived file ([kubeconfig](https://github.com/postfinance/topf/blob/main/docs/commands/kubeconfig.md), [bootstrap tasks](https://github.com/onedr0p/cluster-template/blob/main/template/config/bootstrap/mise.toml)). Since topf can mint one any time from the encrypted bundle, the 12h default would also be fine.

### Checking the result

```bash
talosctl get extensions -n 10.0.11.1            # qemu-guest-agent, iscsi-tools, util-linux-tools
talosctl get discoveredvolumes -n 10.0.11.1     # sda: system partitions only; sdb: the longhorn partition
talosctl get volumestatus -n 10.0.11.1          # the longhorn user volume is ready
talosctl etcd members                           # three members
curl -sk https://10.0.11.10:6443/version        # the VIP answers
kubectl describe nodes | grep Taints            # <none>
just talos::diff --allow-not-ready              # no changes
```

Until a CNI is installed, the nodes are `NotReady`, and topf's pre-flight check refuses them ("no healthy nodes available to process"). `--allow-not-ready` skips that check, so the dry-run can compare the configs. Drop the flag once Cilium is up. The `control-plane` role label also appears only a few seconds after the nodes register, because Talos's `NodeApplyController` retries until the API server answers.

The Proxmox UI then shows each VM's IP under **Summary**, reported by the guest agent.

`talosctl health` won't pass until a CNI is installed; Jonas hit the same thing ([post 2](https://jonashietala.se/blog/2026/05/22/talos_linux_on_proxmox_with_terraform)). **KubePrism** is on by default at `localhost:7445` ([KubePrism](https://docs.siderolabs.com/talos/v1.14/configure-your-talos-cluster/system-configuration/kubeprism.md)). Cilium uses it as its API endpoint.
